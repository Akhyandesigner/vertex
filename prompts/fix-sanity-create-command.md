# Implementation Prompt: Fix Sanity Studio Setup

## Goal

Create a standalone Sanity Studio alongside the existing Next.js app without replacing or modifying the app at the repository root.

## Skills and documentation reviewed

- `sanity-best-practices`
- `references/get-started.md`
- `references/project-structure.md`
- `references/nextjs.md`

## Existing code and configuration inspected

- The root `package.json` defines a Next.js 16 app and does not define a `create-sanity` script.
- No Sanity Studio configuration or `studio/` workspace exists in the repository.
- The npm log for `npm create sanity@latest` shows npm successfully fetched the `create-sanity` package and dependencies, then reports that the child `create-sanity` process exited with code 1. The npm log does not include the CLI's underlying error message.
- Node.js 24.22.0 is installed; the Sanity setup guide requires Node.js 22.12 or newer.

## Decisions and assumptions

- Keep the existing Next.js app at the repository root; do not scaffold or embed the Studio there.
- Create the Studio in a new `studio/` directory using the Sanity CLI directly.
- Use the Sanity project ID and dataset supplied by the user. Do not create or select a project or dataset on the user's behalf.
- Do not inspect, print, or modify `.env.local` secrets.
- If the user has not authenticated with Sanity or does not know the project ID and dataset, stop and explain how to complete those prerequisites rather than guessing.

## Expected files to touch

- New standalone Studio files under `studio/`, generated by the Sanity CLI.
- Do not edit the existing root `package.json`, app files, or lockfile unless the CLI requires a narrowly scoped change and the user approves it.

## Requirements

- Scaffold a clean TypeScript Sanity Studio in `studio/` using the supplied project ID and dataset.
- Preserve existing root Next.js files and configuration.
- Keep Studio dependencies and commands isolated from the Next.js app.
- Surface any CLI failure and its complete diagnostic output; do not treat an npm wrapper error as the root cause.

## Security considerations

- Do not expose Sanity API tokens or other secrets in browser code, output, or committed files.
- Do not overwrite existing project files or choose a project/dataset without the user's confirmation.

## Acceptance criteria

- `studio/sanity.config.ts` and `studio/sanity.cli.ts` exist and point to the user-confirmed project and dataset.
- The Studio's dependencies are isolated under `studio/`.
- The existing root Next.js app remains intact.
- The Studio starts from its own directory with its generated development command.

## Checks

- Run the generated Studio's type check and lint commands if present.
- Run the existing root `npm run lint` to confirm the app remains unaffected.
- Do not claim Studio deployment or live MCP behavior without running those operations.

## Manual test steps

1. In a terminal, change to `studio/` and run `npm install` if the CLI did not install dependencies.
2. Run the Studio's generated development command and confirm the local Studio loads.
3. Confirm the project and dataset shown in Studio match the values supplied by the user.
4. From the repository root, run `npm run lint` and verify the existing app still passes.
